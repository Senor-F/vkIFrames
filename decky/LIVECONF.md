# Live config protocol (plugin -> layer)

The Decky plugin changes layer settings while a game runs. The layer implements the protocol in `src/live_config.cpp`: it reads `VKIFRAME_*` (with the `FRAMEGEN_*` fallback) at startup, re-reads the file when its mtime or size changes, and logs every change as `live: CHANGE KEY: old -> new (live.conf)` in `live.log`.

**The plugin is the only writer today, and it is one-way.** It rewrites the whole file from its saved `settings.json` at every loader start and at every panel change, and never reads `live.conf` back. An edit from outside (a script, the planned `vkiframes-ctl`, the planned overlay) is overwritten at the next loader restart or panel change and is not shown in the panel. Do not change a setting in the panel during a benchmark or a capture; a restart of the loader (a rewrite with the same values) no longer stops a benchmark. The intended fix (the plugin merges the file at start, or the file becomes the source of truth) is an open decision for the owner; it must be settled before the overlay and `vkiframes-ctl` write the same file.

## File
`$XDG_CONFIG_HOME/vkiframes/live.conf` (default `~/.config/vkiframes/live.conf`; the environment variables `VKIFRAME_LIVE_CONF` and `VKIFRAME_LIVE_LOG` override the paths of `live.conf` and `live.log`). Written atomically by the plugin (temp file, then rename).

```
# written by the vkIFrames Decky plugin; do not edit while a game runs
REV=12345
VKIFRAME_ENABLED=1
VKIFRAME_TARGET_FPS=60
...
```

* One `KEY=VALUE` per line. `#` starts a comment. Unknown keys are ignored. The file is a full snapshot, not a patch: every key the layer reads starts at its startup (environment) value at each load, and only the keys present in the file override it. A key missing from the file goes back to the startup value (the log says `back to the startup value`). A tool that writes only its own keys therefore resets all the others; write the whole set, and write a temp file and rename it.
* `REV` increases on every write.

## Layer side
1. Once per second from the present path (or a tiny thread), `stat()` the file. If the mtime or size changed, re-read it. Never block the present path on I/O for more than that one `stat()`.
2. Environment variables are the startup defaults. A key in `live.conf` overrides the environment from then on. Removing the file reverts to the environment values.
3. Live keys (`src/live_config.cpp`): `ENABLED`, `TARGET_FPS`, `MAX_SYNTHETIC`, `BASE_FPS_CAP`, `MIN_GAIN`, `PHASE_LOCK`, `PHASE_OFFSET`, `INTERP_BIDIR`, `CMD_BUFFERS`, `SYNTH_MARGIN`, `STATS`. Other keys (`OPTICAL_FLOW` (old names `INTERPOLATE`, `WARP`), `FLOW_LEVEL`, `EXPERIMENTAL`, `EXTRAPOLATE`, `UI_MASK_THRESHOLD`, `ONESIDED_FILL`) are read at game start. `INTERP_BIDIR` (old alias `WARP_BIDIR`) applies from the next pair; the others apply on the next present; `SYNTH_MARGIN` is 0..0.45. Use the next-swapchain/next-pair rule where a buffer must be rebuilt.
4. `ENABLED=0` must behave like bypass: native frames pass straight through, no added latency.
   The default of `ENABLED` is 1 (the layer works as soon as it is loaded, which needs `VKIFRAME_ENABLE=1` in the process); the panel's default and its "reset" give the same defaults as the layer (`OPTICAL_FLOW` is 0 in both). `tests/test_defaults.cpp` (a ctest) fails the test suite when a default or a range in `settings_schema.json` differs from the layer's.
5. Clamp bad values to the same ranges as `settings_schema.json`; never crash on a malformed line. A value is a number only when it is digits, a sign, a point and an exponent (no `nan`, `inf`, hex, empty value or text after the number); otherwise the line is invalid and the previous value stays. The same rule is used for the start-of-game keys and for the `MAX_SYNTHETIC` line that sizes the swapchain at game start (a line the live parser ignores sets nothing there either; the last valid line counts), and for the `VKIFRAME_*` environment variables. `BASE_FPS_CAP` below 1 is off. At most 64 KiB of the file are read (complete lines only), a line with a NUL byte is ignored, `live.log` never gets control characters from the file, a read makes at most 10 notes about bad lines, and a FIFO or other special file in the place of `live.conf` or `bench.req` is refused without blocking (the file is opened with `O_NONBLOCK`).
6. Optional status (layer -> plugin): write `~/.config/vkiframes/status.json` about once a second, e.g. `{"native_fps":42.1,"output_fps":60.0,"k":1,"mode":"interp","enabled":1,"refresh_hz":60.00,"bench":"","synth_capacity":4}`. `mode` is `interp`, `extrap`, `bypass` or `off`; `refresh_hz` is 0 when the swapchain's refresh rate is unknown. The plugin shows it as is.
   `synth_capacity` is the most synthetic frames per game frame this game's swapchain can hold (0 = not known, no frame holding). **`MAX_SYNTHETIC` does two things:** at game start its value (live.conf over the environment) is the *request* the swapchain is built for (`C = min(limit, max(request, 4))`, the limit is 4, or 10 with `EXPERIMENTAL`; `EXPERIMENTAL` alone adds no images); while the game runs the live value is clamped to the capacity actually granted (`C` limited by the images the driver gave), with one log line per value, and the panel says so: more needs a game restart. If the driver grants too few images for even one synthetic frame, frame holding is off for that swapchain (pass-through, `synth_capacity` 0). Known limits: a smaller swapchain lowers the running `MAX_SYNTHETIC` for good (it does not rise again after a later bigger swapchain until live.conf changes); a swapchain recreated mid-game re-reads live.conf, so a value raised there since the start can raise its capacity without a restart.
7. Benchmark (plugin or script -> layer): the request is **not** in `live.conf`. It is the file `bench.req` in the same folder (next to `live.conf`; 0600, one line: the request number and a newline; written by temporary file and rename by the plugin and by `scripts/vkiframes-bench.sh`). The layer checks it in the same once-a-second poll (one `stat()`; the file is read when its mtime, size or inode changed; no symlink, own file). A new non-zero number (not the one in the file when the game started, not the last one handled) asks for one run (a new number that arrives while a run is going is acknowledged and ignored: ask again when it is done); `0` written while a number was there stops a running run (`--cancel`); anything that is not a whole number from 0 to 4e12 is ignored and logged. It is not a setting: it moves no live value and cannot count as a changed setting, so a panel write or a loader restart cannot stop a run by itself. A run stops only when a setting changes (a live value, `ENABLED` included, differs from what the file says and the user changed it), when `bench.req` becomes `0`, or when the game closes its swapchain. While a run is going a `live.conf` write that changes no value leaves `ENABLED` to the run (it switches `ENABLED` itself). A `BENCH=` line in `live.conf` (an older plugin or script) is ignored and logged once. `status.json` carries `"bench"` (warmup, settle, off, on, done, aborted, or empty) and the layer writes `bench.json` (numbers only) next to it. `STATS=1` writes `stats.jsonl`, one record a second.

## Keeping the plugin in step
`settings_schema.json` lists every setting the plugin shows (key, label, type, default, min, max, step). When a `VKIFRAME_*` setting is added, renamed, removed, or its default or range changes, update `settings_schema.json` in the same change. The plugin needs no other edit.
